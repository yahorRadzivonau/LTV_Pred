# Задание: четыре новые таблицы для графиков в BigQuery

Добавить в терраформ четыре таблицы в датасет `ad_hock_tables`, рядом с уже
существующими. **Существующие таблицы не трогать** — ни `ml_web_predictions`,
ни `ml_web_weekly_curve`.

```
project : appsflyer-data-411716
dataset : ad_hock_tables
```

| таблица | разбивка | ячеек | ожидаемо строк |
|---|---|---|---|
| `ml_web_weekly_curve_geo` | когорта × страна | ~630 | ~66 000 |
| `ml_web_weekly_curve_campaign` | когорта × кампания | ~680 | ~71 000 |
| `ml_web_weekly_curve_ad` | когорта × объявление | ~470 | ~49 000 |
| `ml_web_weekly_curve_full` | когорта × воронка × источник × страна × кампания × объявление | **~3 890** | **~408 000** |

Все четыре — та же понедельная кривая, что в существующей `ml_web_weekly_curve`
(одна строка = ячейка × неделя жизни 0..104), но с другими измерениями.
Перезаписываются целиком при каждом обновлении, инкрементальной догрузки нет.

## Общая часть схемы — одинакова во всех четырёх

Эти 12 колонок идут во ВСЕ четыре таблицы, все `NULLABLE`:

| колонка | тип | описание |
|---|---|---|
| `week` | INTEGER | неделя жизни когорты, 0..104 |
| `n_base_payer` | INTEGER | размер ячейки: сколько человек купили подписку |
| `sample_grade` | STRING | достаточность выборки: `insufficient` / `rough` / `directional` / `reliable` — см. ниже |
| `rebills_base` | FLOAT | человек, платящих базовую подписку в эту неделю |
| `rebills_ups` | FLOAT | платежей по апселлу в эту неделю; ноль вне чекпоинтов 2/6/10/… |
| `rebills_base_cum` | FLOAT | накопленным итогом |
| `rebills_ups_cum` | FLOAT | накопленным итогом |
| `active_share` | FLOAT | `rebills_base / n_base_payer` — доля ячейки, ещё платящая |
| `revenue_week` | FLOAT | выручка за неделю, USD |
| `revenue_cum` | FLOAT | выручка накопленным итогом, USD |
| `source` | STRING | `fact` / `model` / `no_payers` |
| `evidence` | STRING | `web_data` до недели 9, дальше `ios_tail_extrapolation` |

`sample_grade` — новая колонка, которой нет в существующей таблице. Значения:

```
insufficient   менее 30 плательщиков   ошибка выборки ±26% и хуже
rough          30–99                   ±14–26%
directional    100–299                 ±8–14%
reliable       300 и больше            ниже собственной ошибки модели (8.6%)
```

## Настройки для всех четырёх

- **Партиционирование: не нужно.** Даже самая большая таблица — ~408k строк,
  единицы-десятки МБ, и переписывается целиком.
- **Кластеризация:** указана выше для каждой.

  Оговорка, проверенная на соседней таблице: **кластеризация НЕ сортирует вывод
  `SELECT *`.** Она про отсечение блоков при фильтрах, а не про порядок строк.
  Нужен предсказуемый порядок — только `ORDER BY` в запросе или во вью.

- Все колонки `NULLABLE`, включая `week`. Загрузчик пишет весь набор как
  NULLABLE, и если в терраформе поставить `REQUIRED`, load job упадёт на
  несовпадении схемы.

---

## Чего делать НЕ надо

- Не менять `ml_web_predictions` и `ml_web_weekly_curve` — обе работают и залиты.
- Не добавлять `sample_grade` в существующую `ml_web_weekly_curve`: это
  потребовало бы её перезаливки, а она сейчас консистентна с
  `ml_web_predictions`. Новая колонка только в четырёх новых таблицах.
- Не заводить партиционирование по `cohort_date`: когорт всего 16, партиции
  вышли бы по паре тысяч строк.

## Контекст, зачем `_full` такая большая

Это **демонстрационная** таблица. При разбивке по всем шести измерениям
получается 3 887 ячеек на 8 281 плательщика — **2.1 человека на ячейку**.
Почти в каждой строке `sample_grade = insufficient`.

Она сделана специально, чтобы было видно: «разбить по всему сразу» не работает,
данные рассыпаются в пыль. Не ошибка конфигурации, а наглядное пособие.

После создания таблиц сообщите — под них будет написан загрузчик по образцу
`web/v3/upload_weekly_curve.py` (превью по умолчанию, запись только с `--write`,
жёсткая привязка к одной таблице).
