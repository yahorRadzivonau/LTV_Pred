# WEB_V3_SPEC — по-человечная модель веба

Спека итерации. Цель: заменить агрегатную формулу веба (`факт × глобальный
множитель`) на по-человечный расчёт по образцу iOS, где работают рычаги и
`hr` считается по когортам.

**Железное правило итерации:** `web/v2/`, `reports/web_v2/`,
`data/raw/appsflyer_captured_events_with_trial_2026-07-20.parquet`,
`data/raw/bq_appsflyer_person_dim_*.parquet` и таблица BigQuery
`ad_hock_tables.ml_web_predictions` — **не трогаются**. v2 остаётся живым и
воспроизводимым для сравнения. Всё новое — в новых директориях.

## 1. Формула

### Было (v2)

```
S[k]      = MAP.predict(h_base_web, ВСЕ когорты одним пулом)   -> одна кривая на всех
C[k]      = 1 + S[1] + ... + S[k]                              -> ожидаемое число платежей
LTV(N)    = факт_ячейки_сегодня × C[N] / C[age]
```

Цена сокращается в отношении. Рычаги схлопываются в пул. Вся `h_base` сжата в
таблицу ~65 чисел (горизонт × возраст). Ячейка из 2 человек умножает их факт
на 5.33.

### Стало (v3)

```
риск[j]        = clip( mult_комбо × h_base[j] × hr_когорты , 0.001, 0.999 )

S_комбо[k]     = Π_{j=1..k} ( 1 − риск[j] )

S_ячейки[k]    = Σ_комбо  w_комбо × S_комбо[k]

LTV_человека(N) = trial_amt + Σ_{k=0..N} S[k] × rate[k]        (S[0] = 1)

LTV_ячейки(N)   = среднее по людям ячейки
```

где:

| символ | что | скоуп |
|---|---|---|
| `h_base[j]` | базовый риск на ступени j | один на весь веб |
| `mult_комбо` | множитель рычагов (funnel × utm × geo × billday) | человек |
| `hr_когорты` | отклонение когорты от портфеля, усадка `K_SHRINK` | **когорта** |
| `w_комбо` | доля людей этого типа в ячейке | ячейка |

**`hr` считается на когорте, множители — на людях ячейки.** Скоупы обязаны
различаться: `hr`, посчитанный на ячейке, впитает эффект её же рычагов и
задвоит его (см. докстринг `ios/validation/segment_backtest.py`, там это уже
реализовано как `app_hr()` + `segment_curve()` — переиспользуем паттерн).

Побочный эффект, который и нужен: ячейка из 2 человек даёт `n_seen ≈ 6`,
`hr = exp(log_hr × 6/(6+800)) ≈ 1` — она автоматически откатывается к
портфельной кривой со своими рычагами, вместо усиления собственного шума.

### Деньги

```
rate[k] = 9.99                              каждую неделю, пока жив
        + 11.99 на k ∈ {0, 4, 8, 12, ...}   если у человека есть апсейл
trial_amt = 0.99 на k=0                     если платный триал; НЕ проецируется
```

Апсейл — **чекпоинтами**, не `11.99/4` размазанным: размазывание завышает
первые 3 недели (реально списаний до 4-й недели нет). Механика `MONTH_STEP=4`
уже есть в v2.

Апсейл пока **не отдельная кривая** — привязан к дожитию базы. Обоснование:
в данных 0 из 1417 случаев, где апсейл пережил базу. Отдельная кривая +
рычаг «с апсейлом / без» — следующая итерация.

## 2. Знаменатель (фикс регрессии)

**Что сломано:** `web/v2/pull_ltv_v2_population.py` тянет популяцию только по
оплаченным событиям, поэтому непла́тящие структурно не попадают.
`n_attributed == n_payers` (3512 == 3512), `ltv_per_attributed_*` завышен
~1.38x, и это сейчас в BigQuery.

**Новое определение — «per trial»:**

```
популяция = все, кто начал триал (ПЛАТНЫЙ $0.99 ИЛИ бесплатный/плейсхолдер $1.00/NULL)
          ∪ все, кто заплатил за основную подписку
```

Текущая выгрузка бесплатные триалы отбрасывает (`amt != 1.00` фильтр) —
нужен **новый пул с ними**.

`first_funnel` для непла́тящих брать из события входа, а не из первого
оплаченного (иначе они все окажутся без воронки и выпадут из разбивки).

## 3. Матрица ступеней

`build_web_se_training.py`: события appsflyer → та же схема, что
`data/se_training.parquet` (15 колонок). Тогда `core/map_model.py` работает
без правок — проверено на `data/golden/golden_all_se_training.parquet`.

Ключевое отличие от v2:

```
app_id = cohort_date        # ← это и включает hr по когортам
```

В v2 веб-матрица имеет `app_id = 'invinci'` единственным значением — отсюда
один `hr` на всё и схлопывание рычагов.

Джойн рычагов из `web_conversions`: `country` → `geo`, `utm_source` →
`media_source`, `funnel_name` → `funnel` (новый), `billing_day_of_month` из
`pay_ts`.

### Фикс правого края (ложные смерти)

Правило разметки даёт 60 дней на возврат (`RETURN_WINDOW_DAYS`), но
цензурирование `weeks_obs >= step_k` гарантирует только 1 неделю. Человек с
платежом 8 дней назад, который вернётся на 20-й день, записан мёртвым.

Замер: **9.4%** строк чистой зоны веба помечены мёртвыми с ещё открытым
окном (iOS — 2.4%; на вебе в 4 раза больнее, потому что он молодой).

**Фикс:** ступень попадает в обучение только если
`(T − pay_ts) >= RETURN_WINDOW_DAYS`, иначе она цензурируется как
«исход ещё неизвестен».

Ожидаемый эффект: дожитие вырастет, прогнозы вырастут. Календарный тест уже
показывает завышение +16% — ложные смерти его частично маскировали. После
фикса завышение станет виднее. Это снятие компенсирующей ошибки, не регресс.

### 736 событий `subscription_started @ $0.99`

Помечать как триал, не как платёж базы — иначе человек получает фантомную
ступень. Проверено: это не дубли `trial_started` (совпадение по времени
только у 1 человека из 736).

## 4. Рычаги

```python
MAP_LEVERS_WEB = ["funnel", "utm_source", "geo", "billday_bin"]
MAP_MIN_ROWS_WEB = 250      # v2/iOS: 2000 — при 13k строк выживут 2 воронки
```

Порядок = порядок residual-цепочки, **не менять**. Каждый следующий рычаг
считается на остатке после предыдущих (`mult = obs/expected`, где `expected`
уже учитывает предыдущие) — защита от задвоения у скоррелированных рычагов.

Воронка первой: это оффер, ближе к причине, почему человек продолжает
платить. Источник — байер, влияет во многом через воронку. Порядок
`funnel → utm` vs `utm → funnel` дёшево прогнать обоими и сравнить.

**Санити ДО бэктеста** (урок бага `rr` в `hybrid.py` — сначала вменяемость,
потом точность): взвешенное среднее множителей каждого рычага в (0.9, 1.1).
Падает — стоп и разбор с владельцем, не подкрутка порога.

Данных на воронку: 21 значение, ≥100 плательщиков у 3, ≥50 у 8, ≥20 у 13.
Топ-5 = 76.6% плательщиков. Ожидаем 5-8 живых категорий + `other`.

Ячеек `воронка × utm` с ≥30 плательщиками всего 11 — но это ограничение на
таблицу, не на модель: множители оцениваются на маргиналах, прогноз ячейки =
произведение. Ячейке не нужны свои данные, чтобы получить осмысленную кривую.

## 5. Тесты

### Основной: LOO по когортам (`validate_loo_web.py`)

Переобучить `h_base` + всю цепочку множителей **без строк целевой когорты**,
предсказать её. Аналог `ios/validation/validate_loo.py`, где LOO по аппам.

Метрика — ближняя точность, а не дальняя: сетка

```
видимых недель данных: 1..8   ×   горизонт: +1, +2, +4 недели
```

Отвечает на «насколько точно я предскажу следующую неделю», а не на «что
будет через полгода». Медиана |отн. ошибки| **и знак** (смещение важнее
модуля).

### Вторичный: календарный (`backtest_web_calendar.py`)

Встать в T, обучиться на `pay_ts < T`, предсказать когорты. Обучение —
**только с 2026-04-13** (до этой даты данные неконсистентны: мало гео, кривые
оплаты — решение владельца, не обсуждается). Отсюда 2-3 точки T, мало.
Держим как индикатор дрейфа, не как основную метрику.

### Сравнение (`comparison_v2_vs_v3.md`)

Три колонки на одних и тех же исправленных данных:

| вариант | что меряем |
|---|---|
| v2-формула (`факт × ratio`) | baseline |
| v3-формула без воронки | вклад по-человечного расчёта |
| v3-формула + воронка | вклад рычага |

Критично: **v2-формулу прогнать на новых данных тоже**, иначе эффект формулы
смешается с эффектом фиксов знаменателя/триала/апсейла.

## 7. Явно НЕ в этой итерации

**Дообучение рычагов от iOS-приора.** Меняет веса, тогда как этапы 4-5 меняют
формулу. Вместе — невозможно атрибутировать результат. Следующей итерацией,
когда LOO уже будет мерить.

Находка, которая уточняет эту будущую работу:

| рычаг | категорий в вебе | покрытие iOS-приором |
|---|---|---|
| `geo` | 56 | **100%** — приор пригоден |
| `billday` | 3 | универсален — пригоден |
| `utm_source` | 9 | **9.1%** — топ веб-источников (`fbbohdan`, `fb-andrii`, `ads-rs`) в iOS не существует, приора нет |
| `funnel` | 21 | в iOS отсутствует как понятие |

То есть «дообучить матрицу iOS» применимо к `geo`/`billday`, а `utm`/`funnel`
учатся с нуля на вебе.

**Марков / серое состояние.** Изначальный замысел (триал → активен → серый →
возврат/смерть) не реализован: `state_from` захардкожен в `"active"`, пять
исходов схлопнуты в бинарь `survived`, дунинг влияет на ярлык и ни на что
больше.

Довод в пользу того, что это стоит сделать — веб и iOS умирают по-разному:

| исход | iOS | Веб |
|---|---|---|
| `voluntary_cancel` | **11.3%** | 1.3% |
| `billing_issue` | 0.5% | **8.3%** |

iOS-юзеры отменяют осознанно, у веб-юзеров падает оплата. Это разные процессы
с разной возвратностью, и на вебе серое состояние — **доминирующий способ
смерти**. Плюс 42 699 событий `billing_issue` в `web_conversions` сейчас
выбрасываются целиком.

В эту итерацию — только дешёвый фикс правого края (§3). Полная машина
состояний — следующей итерацией, когда её можно будет измерить.
