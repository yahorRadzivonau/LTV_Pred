# WEB v3 — документация

Пайплайн прогноза LTV веб-подписок, построенный по-человечно: кривая дожития
считается на уровне подписчика, `hr` — на уровне когорты, деньги — заякорены на
наблюдённой выручке.

Заменяет `web/v2/`. v2 не удалён и остаётся воспроизводимым baseline'ом.

- План итерации, как он был утверждён: [`WEB_V3_SPEC.md`](WEB_V3_SPEC.md)
- Отчёты и замеры: `reports/web_v3/`

---

## 1. Зачем это было нужно

v2 формально использовал MAP-модель, но фактически считал так:

```
LTV(N) = факт_ячейки(возраст) × C[N] / C[возраст]
```

где `C` — **одна глобальная кривая на весь продукт**. Следствия:

- Две ячейки одного возраста получали **побитово одинаковый множитель**
  независимо от воронки, источника и гео. Рычаги вычислялись и выбрасывались.
- Причина найдена: в веб-матрице `app_id` имел **единственное значение**
  `'invinci'`, поэтому `map_model` считал один `hr` на весь продукт, а личные
  множители усреднялись в одну пулированную кривую.
- Ячейка с медианой **2 плательщика** умножала их факт на 5.33 (возраст 3 нед →
  нед 104) без всякой усадки. 133 из 163 ячеек были `low_n`.
- На горизонтах 26/52/104 недель — **ноль** ячеек с фактом.
- Точность веба **никогда не измерялась**: гейт `reconcile_v2.py` проверял
  согласие с golden, а не правильность прогноза.

## 2. Формула

### Дожитие

```
риск[j]      = clip( mult_комбо × h_base[j] × hr_когорты , 0.001, 0.999 )
S_комбо[k]   = Π_{j=1..k} ( 1 − риск[j] )
S_ячейки[k]  = Σ_комбо  w_комбо × S_комбо[k]
```

| символ | что это | скоуп |
|---|---|---|
| `h_base[j]` | базовый риск отвала на ступени j | один на весь веб |
| `mult_комбо` | множитель рычагов (utm × geo × billday) | человек |
| `hr_когорты` | отклонение когорты от портфеля, усадка `K_SHRINK=800` | **когорта** |
| `w_комбо` | доля людей этого типа в ячейке | ячейка |

**`hr` считается на когорте, множители — на людях ячейки. Скоупы обязаны
различаться.** `hr`, посчитанный на ячейке, впитал бы эффект её же рычагов и
задвоил его — та самая ошибка, из-за которой закрыт `ios/alt_models/hybrid.py`.

Побочный эффект, ради которого всё и делалось: ячейка из 2 человек даёт
`n_seen ≈ 6`, то есть `hr = exp(log_hr × 6/(6+800)) ≈ 1`, и откатывается к
портфельной кривой со своими рычагами вместо усиления собственного шума.

### Деньги

```
LTV(N) = наблюдённая выручка на якоре + прогноз приращения за недели якорь+1..N
```

Выручка, которую когорта уже заработала, — это **факт**. Пересчитывать её через
модельные цены и модельное дожитие означает вносить ошибку в число, которое мы
и так знаем. Моделируется только приращение.

Приращение считается на **безусловном** дожитии `S[k]`, а не на условном
`S[k]/S[якорь]`: якорь — это среднее по всем членам ячейки, включая уже
отвалившихся, поэтому и приращение обязано быть на той же базе.

| поток | как входит |
|---|---|
| база | `BASE_PRICE` каждую неделю, пока человек платит |
| апсейл | `UPS_PRICE` на чекпоинтах недель **2, 6, 10, …** (замер: первый апселл на неделе 2, на неделе 0 — ноль) |
| триал | никак — он разовый на неделе 0, то есть всегда уже внутри якоря |

Апселл ездит на дожитии базы: в данных 0 из 1417 человек с обоими потоками имели
последний апселл позже последнего базового платежа.

### Граница evidence

Свой веб-овский `h_base` держится до **ступени 10-11** (`k_max_web`, растёт по мере накопления данных; на 28.07 было 8). Дальше
сращивается хвост iOS, отмасштабированный так, чтобы стыковаться без скачка.

В выходных таблицах это колонка `ltv_{N}_evidence`:
`web_data` до `k_max_web`, `ios_tail_extrapolation` дальше. **Нед 26/52/104 лежат
целиком за границей.**

## 3. Данные

### Источник

Всё из **БК**: `appsflyer-data-411716.silver_layer.web_conversions`, один запрос.
Отдельного пула популяции нет специально — два запроса могли бы описывать разные
снапшоты.

Единственное исключение: `data/se_training.parquet` (матрица iOS, тоже из БК)
читается ради `h_base` для хвоста.

**v3 не читает `data/golden/*`** — распарсенный из сырых Stripe/Solidgate
источник, на котором v2 калибровал форму роста. У golden известный дефект:
`trial_converted` у 814 человек из ~3600 несёт цену полного тарифа вместо
реальной цены триала. v3 эту зависимость убрал.

### Окно

- `WINDOW_START = 2026-04-13` — обучение и отчёты. До этой даты данные
  неконсистентны (мало гео, кривые оплаты). Решение владельца.
- `PULL_FLOOR_DATE = 2025-10-01` — пул тянет **раньше** окна намеренно: человек с
  триалом 10 апреля и первым платежом 20 апреля получил бы неверный `first_date`
  и не ту когорту, если бы пул обрезался по `WINDOW_START`.

### Знаменатель (per-trial)

```
популяция = начавшие триал ЛЮБОГО вида ($0.99 / $1.00-плейсхолдер / бесплатный)
          ∪ купившие базовую подписку
```

Замер на 2026-08-10: **14 127 человек, 60.9% дошли до подписки.**

Колонки названы по тому, что они буквально считают. Имён `is_payer` и
`n_attributed` в v3 нет — именно под ними пряталась регрессия v2:

| колонка | что считает |
|---|---|
| `has_base` | купил $9.99/нед — настоящая конверсия |
| `has_paid_trial` | заплатил разовый триал |
| `has_ups` | взял апсейл |
| `paid_anything` | любые деньги, включая триал-онли. **Только для сверки**, не знаменатель |

### Исключено: продукт B

В потоке было **два продукта**, оба назывались «base»:

| | продукт A | продукт B |
|---|---|---|
| триал | $0.99 | $4.99 |
| подписка | $9.99 | $39.99 |
| каденция | 6 дней (недельная) | **28 дней (месячная)** |
| плательщиков | 6 483 | 231 |
| связь триал→тариф | 78% | 81% |

Продукт B исключён (`EXCLUDE_PRODUCT_B`). Он свёрнут ещё до окна — после
13 апреля в него вошли **2 человека**, а платежи $39.99 в мае-июле это продления
старых подписок. Из пула убирает 873 человека, из популяции — 2.

Членство определяется по **цене**, никогда по каденции: каденция выводится из
зазоров между собственными платежами человека, то есть неизвестна для 42.6%
сделавших один платёж, а для остальных утекает исход.

### Цензурирование

`RETURN_WINDOW_DAYS = 21`. Ступень идёт в обучение, только если ей исполнился
21 день — **строго по времени, независимо от того, что произошло**.

Почему не 60 как в iOS: продукт недельный, и 99.5% всех продолжений укладываются
в 21 день (медиана 9, p95 20, p99 36). 60 дней калиброваны под месячные и годовые
мобильные подписки.

**Ловушка, в которую я попал и из которой выбрался** (записано, чтобы не
повторили): правило «оставляем строку, если исход известен — либо есть следующий
платёж, либо окно истекло» выглядит разумным и **катастрофически смещено**.
Выживший подтверждается за неделю, смерть требует полного окна, поэтому правило
оставляет почти всех выживших и выкидывает большинство смертей. Замер: удалило
84% смертей, доля смертности в чистой зоне упала с 0.182 до 0.030, `h_base`
занулился на ступенях 2-8. **Цензурирование не должно зависеть от исхода.**

## 4. Рычаги

```python
MAP_LEVERS_WEB   = ["utm_source", "geo", "billday_bin"]
MAP_MIN_ROWS_WEB = 250
```

Порядок = порядок residual-цепочки: каждый следующий рычаг фитится на остатке
после предыдущих (`mult = obs/expected`, где `expected` уже несёт предыдущие).
Это защита от задвоения у скоррелированных рычагов.

Порог 250 вместо 2000 у iOS/v2: веб-матрица ~12k обучающих строк, при 2000
выжили бы 2 категории.

**Санити перед любыми замерами точности** (урок бага `rr` в `hybrid.py`):
взвешенное среднее множителей каждого рычага должно лежать в (0.9, 1.1).
Текущие (10.08): `utm_source` 1.008, `geo` 0.980, `billday_bin` 0.999.
Падает — стоп и разбор, а не подкрутка порога.

### Воронка: замерена, оставлена вне

| сравнение | \|ошибка\| | вывод |
|---|---|---|
| рычаги как группа vs без рычагов, **LTV** | 2.5% -> 1.9% | помогают |
| те же, дожитие | 6.1% -> 7.2% | **мешают** |
| **воронка** поверх utm+geo+billday, дожитие | 7.2% -> 10.2% | заметно хуже |
| **воронка**, LTV | 1.9% -> 2.2% | хуже |

Рычаг не инертен — его множители дают размах 0.88–1.29. Но ставки **не переживают
leave-one-cohort-out**: 5 выживших категорий на ~12k строк подгоняются под шум
конкретных когорт. Тот же паттерн, что iOS показал на своём LOO.

Диагноз нарезки: выжившие категории (`device-security-check`,
`device-security-check-gate`, `device-security`, `device-security-gate`) —
**A/B-варианты одной воронки**, а реально разные (`world-cup`, `watch-games`,
`product`) свалены в `other`.

**Позиция владельца, записанная для следующей фазы:** вернуться к воронке-рычагу,
а не отбрасывать. Возражение про варианты не проблема — семьи `device-security*`
и `detect-security*` это **85% популяции**, так что разрешение тратится там, где
бизнес.

**Важно на будущее:** настоящий сигнал воронки сидит в **конверсии**, а не в
удержании после конверсии. Конверсия по воронкам от 20.2% до 72.5% — разброс
**3.6x**, против 1.5x у множителей hazard'а. Усадка конверсии ячейки к средней по
её воронке, вероятно, ценнее любого hazard-рычага.

Включить воронку обратно: добавить `"funnel"` в `MAP_LEVERS_WEB`. Больше ничего
менять не нужно, и таблицы режутся по воронке в любом случае — быть измерением
отчёта и быть рычагом модели это разные вопросы.

## 5. Точность

**Первое измеренное число точности веба в этом проекте.**

LOO по когортам: `h_base` и вся цепочка множителей переобучаются **без строк
целевой когорты**, затем эта когорта предсказывается.

Замер на данных **2026-08-10** (события по 09.08):

| метрика | v2-формула | **v3-формула** |
|---|---|---|
| дожитие, \|ошибка\| | 7.6% | **7.2%** |
| дожитие, смещение | −1.4% | −2.0% |
| LTV, \|ошибка\| | 2.5% | **1.9%** |
| LTV, смещение | −1.5% | −1.5% |

n = 220 фолдов, 14 когорт. Обе формулы на одних данных и одних фолдах — разница
относится к формуле, а не к фиксам данных.

Ошибка по LTV **ниже**, чем по дожитию: прогноз заякорен на факте, моделируется
только приращение.

**Отрыв v3 сокращается по мере накопления данных.** На июльском замере (n=101,
9 когорт) было 11.2% против 8.6% по дожитию — разрыв 2.6 п.п.; сейчас 7.6%
против 7.2% — 0.4 п.п. Обе формулы стали точнее, но v2 подтянулась сильнее.
Правдоподобное объяснение: главное преимущество v3 — per-cohort `hr` — тем
заметнее, чем хуже портфельная кривая описывает конкретную когорту, а с ростом
выборки портфельная кривая сама по себе стала точнее. Проверять это отдельно не
пробовал, так что это гипотеза, а не вывод.

### Чего НЕ измерено

**Календарный дрейф.** iOS на своём календарном бэктесте завышает на **+16%** на
нед12 и **+50%** на нед26. У веба такого теста нет: при обучении с 13 апреля на
него хватает 2-3 точек T. Это главное открытое неизвестное.

LOO проверяет обобщение на **не виденную когорту-современницу**, но не на
будущее. Дрейф портфеля он поймать не может по построению.

### Контракт изоляции

- Ничего под `web/v3/` **не пишет** за пределы `data/web_v3/` и `reports/web_v3/`.
- **`core/map_model.py` не трогается ни на символ.** Вебу нужен свой список
  рычагов и свой порог, а они там модульные глобальные, общие с iOS-моделью —
  их мутация поехала бы на все iOS-отчёты в том же процессе. Поэтому
  `ltv_v3/map_web.py` это копия. Тот же приём уже применён в
  `ios/validation/segment_backtest.py`.
- Из `core` берётся только чистое: `common.empirical_hbase`, `HMAX`, `K_SHRINK`.

Проверка после любой правки:

## 8. Известные ограничения

1. **Календарный дрейф не измерен** (см. §5). Главное открытое место.
2. **Хвост заимствован.** Всё за ступенью 8 — форма iOS. Нед 26/52/104 это
   допущение, а не измерение.
3. **Ячейки тонкие.** В таблице C 302 из 340 помечены `low_n` (<40 плательщиков),
   64% ячеек имеют 1–9 плательщиков. Усадка `hr` не даёт им улетать, но данных в
   них мало — читать поячеечно только с оглядкой на `n_base_payer`.
4. **`REFUND_HAIRCUT = 0.00913` — костыль.** В appsflyer нет событий рефанда
   вообще; константа выведена с golden-стороны. Единственное число в v3, пришедшее
   не из БК.
5. **Марков не построен.** `state_from` захардкожен в `"active"`, пять исходов
   схлопнуты в бинарь, дунинг влияет на ярлык и ни на что больше. На вебе это
   особенно жаль: `billing_issue` — **доминирующий способ смерти** (8.3% против
   0.5% на iOS, где люди отменяют осознанно — 11.3% против 1.3%). 85 832 события
   `billing_issue` сейчас используются только для разметки.
6. **Апселл не имеет своей кривой** — ездит на дожитии базы. Оправдано данными
   (0 из 1417 пережили базу), но при росте потока стоит пересмотреть.

## 9. Ошибки, найденные по ходу

Записаны, потому что все они выглядели правдоподобно и были пойманы только
потому, что цифры не сходились.

| ошибка | как проявилась | причина |
|---|---|---|
| знаменатель только из плательщиков | `n_attributed == n_payers`, per_attributed завышен 1.38x | пул популяции шёл по оплаченным событиям |
| цензурирование по исходу | `h_base` занулился на ступенях 2-8 | выживший подтверждается за неделю, смерть — за окно |
| обрезка истории при подсчёте факта | обе модели ровно +29% завышения | фильтр по зрелости применялся до взятия `max_step` |
| условное дожитие в деньгах | LTV +13.9% при точном дожитии | якорь на всей популяции, приращение на выживших |
| апселл на неделе 0 | завышение коротких горизонтов | реально первый апселл на неделе 2 |
| якорь и цель на разных подмножествах | разрыв из состава, не из модели | разные зрелые популяции для двух чисел |
| цены измерены не на той выборке | «база $10.57», «есть тариф $4.99» | замер по всему пулу вместо популяции в окне |

Два вывода:

- **Агрегатные медианы обманывают.** Дважды за итерацию я делал неверный вывод из
